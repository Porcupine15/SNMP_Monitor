# SNMP Monitor

Веб-приложение для мониторинга коммутаторов, маршрутизаторов и принтеров по
SNMP. Backend написан на FastAPI, данные хранятся в PostgreSQL, production-
интерфейс публикуется через HTTPS reverse proxy.

Фронтенд расположен в `frontend/`: `index.html` содержит разметку,
`styles.css` — оформление, `app.js` — логику интерфейса. Файлы доступны через
`/static/` и не дублируются в backend.

## Документация по запуску

Для локальной разработки используйте `docker compose up --build`. Создайте
локальный `.env` из `.env.example`, но не переносите его в production.
После применения миграций запущенным backend первый локальный admin можно
создать интерактивно в другом терминале:

```bash
docker compose exec backend python -m app.bootstrap_admin \
  --username local-admin
```

Для постоянного запуска в Debian VM на Proxmox см.
[DEPLOYMENT.md](DEPLOYMENT.md). Для корпоративной сети обязательна подробная
инструкция [CORPORATE_DEPLOYMENT.md](CORPORATE_DEPLOYMENT.md): HTTPS, ACL,
новые секреты и БД, явная миграция, backup/restore, пилот и откат.

В production публичная регистрация отключена. После запуска PostgreSQL и
явной Alembic-миграции первый администратор создаётся интерактивно:

```bash
export ADMIN_USERNAME='snmp-admin'
export ADMIN_EMAIL='snmp-admin@corp.example'
docker compose -f compose.production.yml -f compose.tls.yml \
  run --rm backend python -m app.bootstrap_admin \
  --username "$ADMIN_USERNAME" --email "$ADMIN_EMAIL"
```

Затем backend и HTTPS proxy запускаются командой из корпоративной инструкции.
Дополнительных пользователей создаёт администратор через интерфейс.

Для локальной разработки используйте только собственную тестовую подсеть. В
корпоративной среде сканируйте лишь явно согласованный CIDR, например
`10.20.30.0/24`, входящий в `ALLOWED_NETWORKS`. Один запуск ограничен 1024
адресами.

## Что уже работает

- JWT-авторизация и защищённые API;
- обнаружение доступных SNMP-устройств (v1/v2c);
- периодический ICMP-опрос и журнал смены статуса;
- таблица портов: состояние, скорость, PVID, количество и список FDB MAC,
  а также IP, сопоставленные с MAC через ARP;
- список принтеров и чтение уровня расходника, если устройство поддерживает
  стандартный Printer-MIB;
- серверный ping выбранного IP-адреса;
- обнаружение обычных клиентов локальной сети по ICMP/ARP;
- локальный LAN-агент для передачи MAC и имён из ARP-таблицы хоста;
- роли пользователей, аудит, история доступности и CSV-экспорт;
- настраиваемые интервалы опроса и параметры ping.

## Разработка без оборудования

В «Настройках» доступен demo-коммутатор. Он не обращается к сети и показывает
типичный снимок портов с PVID, MAC и ARP-IP. Проверки backend запускаются так:

```bash
docker compose exec -w /app -T backend pytest -q
```

Роли: первый production-пользователь создаётся CLI-командой bootstrap и
получает роль `admin`; остальные создаются администратором. Публичную
регистрацию в production включать нельзя. Добавлять устройства могут `admin`
и `operator`.

## Клиенты локальной сети

Страница «Клиенты сети» сканирует подсеть без SNMP. Для локальной разработки
MAC-адреса можно передавать агентом с Mac/Linux-хоста, имеющего L2-видимость:

```bash
export SNMP_MONITOR_URL='http://localhost:8000/api/clients/agent-sync'
export LAN_AGENT_TOKEN='<ОТДЕЛЬНЫЙ_ТОКЕН_АГЕНТА>'
python3 agent/lan_agent.py
```

Не передавайте агенту весь production `.env`. Для корпоративного запуска
задайте HTTPS URL и храните только отдельный `LAN_AGENT_TOKEN` в защищённом
конфигурационном файле/службе. Агент не требует пароль от роутера или Wi-Fi.
Клиент считается устаревшим, если не наблюдался более 10 минут.

## Миграции и реквизиты

Alembic-миграции находятся в `backend/alembic`. В production они применяются
явной одноразовой Compose-командой до запуска backend; точная команда приведена
в [CORPORATE_DEPLOYMENT.md](CORPORATE_DEPLOYMENT.md#7-первый-запуск-бд-миграция-admin-https).

Укажите `CREDENTIALS_ENCRYPTION_KEY` в `.env` до ввода SNMP community или
паролей v3: новые реквизиты будут храниться в БД зашифрованными Fernet.
Сгенерировать ключ можно командой из `.env.example`.

## Зависимости

Прямые зависимости описаны в `backend/requirements.txt`, а production-образ
устанавливает проверенный `backend/requirements.lock` с SHA-256. После
осознанного изменения версий пересоздайте оба lock-файла для Python 3.11/Linux
командами, записанными в их заголовках, затем запустите тесты и `pip-audit`.
`requirements-dev.lock` дополнительно содержит только инструменты разработки.

## Важные ограничения

- Trunk/Access пока являются локальной меткой порта. Изменение конфигурации
  коммутатора через SNMP SET намеренно не включено до выбора модели устройства
  и проверки её OID на пилотном устройстве.
- VLAN, ARP и тонер сильно зависят от производителя. Сейчас показывается
  стандартный PVID из Q-BRIDGE-MIB; tagged VLAN и vendor-specific данные будут
  добавлены профилями оборудования после получения моделей/OID.
- Новые SNMP-реквизиты шифруются Fernet перед сохранением в БД. Ключ
  `CREDENTIALS_ENCRYPTION_KEY` необходимо включить в recovery-план и хранить
  отдельно от дампа в менеджере секретов: без него расшифровать community и
  пароли SNMPv3 невозможно.
